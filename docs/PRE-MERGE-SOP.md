# SOP — pre-merge tests, and the evidence to attach

The rule this exists to serve: **a PR carries proof its suites passed before a
reviewer is asked to look at it.** The proof is one file, `RESULTS.md`, and it
records what ran, which branch, and *where it ran*.

Everything below is verified against the scripts as they are today, not against
intent. Where a repo behaves differently from the others, that is called out
rather than smoothed over.

---

## 1. What to run

From inside the repo, on the branch you intend to raise:

```bash
export NUTANIX_USER=<pc-username>
export NUTANIX_PASSWORD=<pc-password>

./hack/dev-vm/<repo>-pc-test.sh run                        # the full gate
./hack/dev-vm/<repo>-pc-test.sh run --suites "unit lint"   # a quick subset
./hack/dev-vm/<repo>-pc-test.sh run --pr 1234              # + comment on the PR
```

or through pre-commit, which is the same script behind a hook. **The hook id is
not the same in every repo** — konvoy2 and CAREN call it `dev-pre-pr`,
kommander calls it `kommander-pc-test`:

```bash
pre-commit run dev-pre-pr --hook-stage manual                     # konvoy2, CAREN
TEST_TARGET=local pre-commit run dev-pre-pr --hook-stage manual   # no VM
pre-commit run kommander-pc-test --hook-stage manual              # kommander
```

Both are **manual-stage** hooks on purpose: the suites take minutes to hours,
so they run when you ask, never on every commit.

## 2. Where it runs, and how the result says so

| Target | How | `RESULTS.md` records |
|---|---|---|
| Dynamic Prism Central VM (default) | `run` | `**Runner:** dynamic PC VM (16 vCPU / 32G, Ubuntu 24.04, CI-parity devbox toolchain)` |
| Your own machine | `TEST_TARGET=local` | `**Runner:** local (Darwin arm64, 12 cores)` |

That `Runner:` line is the attribute a reviewer checks to know whether the
evidence came from a CI-parity VM or a laptop. It is generated by the script,
not typed by hand.

**kommander has no local mode.** Its `pc-test.sh` has no `TEST_TARGET`; run
`kommander-test-vm.sh <suite>` directly on a machine or long-lived DevVM
instead. Only the VM `Runner:` line exists there.

## 3. Which suites to run, per repo

| Repo | Suite labels | Env override | Full gate |
|---|---|---|---|
| konvoy2 | `precommit` `ci` `docstest` `unit` `lint` `build` | `KONVOY2_TEST_SUITES` | ~1-1.5 h |
| CAREN | `precommit` `unit` `lint` `helm` `e2e-docker` | `CAREN_TEST_SUITES` | — |
| kommander | `unit` `lint` `kuttl` `bootstrapper` (+6 kuttl sub-suites) | `KOMMANDER_TEST_SUITES` | ~3 h |

Narrower selection inside a suite:

- **CAREN e2e** — ginkgo labels compose into a matrix:
  `provider:` Docker/AWS/Nutanix × `cni:` Cilium × `addonStrategy:`
  HelmAddon/ClusterResourceSet. Pick a cell with
  `make e2e-test E2E_LABEL='provider:Docker' E2E_FOCUS='Quick start'`.
- **konvoy2 cloud e2e** — not in this gate at all. It is CI-only, gated on the
  GitHub PR labels `runs-e2e-tests` / `runs-e2e-upgrade-tests`, because it
  needs cloud credentials.

## 4. What gets tested — and the difference that bites

- **konvoy2 and CAREN** ship your **working tree**: committed, uncommitted and
  untracked. No commit, no push. The script sends a delta (a bundle of unpushed
  commits, a patch of tracked edits, a tarball of untracked files), so a
  multi-GB checkout costs a few hundred KB. `RESULTS.md` says when a run came
  from a dirty tree.
- **kommander** clones the **pushed** branch. Commit and push first; the script
  warns if your tree is dirty, and the dirty part is not tested.

## 5. Attaching the evidence

`test-results/<timestamp>/RESULTS.md` is the artifact. Either:

```bash
./hack/dev-vm/<repo>-pc-test.sh run --pr 1234        # auto-comments it
gh pr comment 1234 --body-file test-results/<ts>/RESULTS.md   # or by hand
```

`--pr` posts the file verbatim as a PR comment, so the table and the `Runner:`
line render inline.

## 6. The evidence set to produce

One PR per repo, each showing the same three things:

1. **The invocation** — terminal capture of the command, with the suite
   selection visible (`--suites "unit lint"`, or `E2E_LABEL=…` for a CAREN e2e
   run). This is what shows labels being used to narrow scope.
2. **The execution** — terminal capture mid-run: the VM being created, the
   suites starting, one suite finishing.
3. **The result** — the `RESULTS.md` comment on the PR, showing the suite
   table, PASS/FAIL per suite, and the `Runner:` line proving where it ran.

Produce at least one PR on the **local** target and one on the **dynamic VM**
target, so the `Runner:` line differs between them and the attribute is
demonstrably doing its job. kommander can only supply the VM variant.

## 7. Known state, 2026-09-01

- `--pr` was documented in konvoy2's README but not implemented; it has now
  been ported to konvoy2 and CAREN from kommander's version. CAREN's README did
  not advertise it and still does not.
- kommander's `hack/dev-vm/` lives on the `feat/dev-vm-pre-pr-testing` branch
  (commit `fb0a7efe1`), not on a release branch.

### Example PRs carrying evidence

| Repo | PR | Result | Runner |
|---|---|---|---|
| konvoy2 | [#4890](https://github.com/mesosphere/konvoy2/pull/4890) | lint PASS 147s | dynamic PC VM, 16 vCPU / 32G |
| kommander | [#7869](https://github.com/mesosphere/kommander/pull/7869) | lint FAIL 28s → PASS 169s | dynamic PC VM, 16 vCPU / 64G |

kommander's PR is the more useful example: the first run **failed in 28s**
because `kommander-test-vm.sh` ran `make capi.clusterclass-templates.update`
unconditionally, and that target exists only on `main`, not on `release-2.18`.
The gate caught it before the PR was reviewed. The fix (`38089ac94`) probes
with `make -n` and falls back to plain `make lint`; the re-run is green. Both
comments are on the PRs, so the failure and the fix are both visible.

CAREN is deliberately absent. Its `hack/dev-vm` script hardcoded a PC URL and
subnet / PE-cluster / image UUIDs as defaults, and CAREN is a **public**
repository. Those defaults have to become required env vars with placeholder
docs before a CAREN PR can carry this evidence.
